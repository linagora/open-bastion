ob-post-upgrade
===============

Synopsis
--------

::

   ob-post-upgrade [--dry-run]

Description
-----------

Installing the package is not always enough. Some of what a host needs lives
outside it: ``/usr/local/sbin/ob-ssh-principals`` is generated by
:doc:`ob-bastion-setup(8) <ob-bastion-setup>` or
:doc:`ob-backend-setup(8) <ob-bastion-setup>`, so an upgrade replaces the
daemon it talks to and leaves the helper as it was.

Until this command, the only cure was "re-run the setup script with the
arguments you used before" — and an operator who deployed through
:doc:`ob-builder(1) <ob-builder>` months ago does not have them.

``ob-post-upgrade`` needs none. Everything it re-asserts is derivable from the
host: the shipped helper text, the tmpfiles rule, the socket unit, and the
ownership of the fingerprint spool. It reads
``/etc/open-bastion/openbastion.conf`` for exactly one value — ``node_role`` —
to choose the bastion or the backend helper, and writes nothing to it.

On a bastion whose sshd forces sessions through
:doc:`ob-session-recorder(8) <ob-session-recorder>` (the ``ForceCommand`` of
the setup's drop-in), it also makes :doc:`ob-login-shell(8) <ob-login-shell>`
the login shell of SSO users: it adds
``force_shell = /usr/sbin/ob-login-shell`` to
``/etc/open-bastion/nss_openbastion.conf`` when that key is missing, lists the
launcher in ``/etc/shells``, and restarts :manpage:`nscd(8)` if it runs.
Without it, sshd runs the recorder through bash or zsh, which read the user's
own startup files first. Nothing else in that file changes, and a
``force_shell`` set to another value is left alone, with a warning. This too
is derived from the host: the ``ForceCommand`` says it records.

It is idempotent. Run it as often as you like; on a host that is already
current it reports that and changes nothing.

Cron jobs of 0.6
----------------

Up to 0.6 the setup scheduled two jobs with cron:
``/etc/cron.d/open-bastion-krl`` (under maximum security: refresh the key
revocation list with a generated ``/usr/local/bin/open-bastion-refresh-krl``)
and ``/etc/cron.daily/open-bastion-audit-rotate`` (``--enable-audit-trace``).
Both are now systemd timers, ``ob-krl-refresh.timer`` and
``ob-audit-rotate.timer``. The old jobs keep working after the upgrade; this
command replaces them:

* The KRL job's interval (``*/N`` in the minute field) is carried over: when
  it is not 30 minutes it is written to
  ``/etc/systemd/system/ob-krl-refresh.timer.d/schedule.conf``. A rotation
  moved to ``/etc/cron.weekly`` becomes a weekly timer the same way.

* The timer is enabled and started, and the old job is removed only once the
  timer is enabled and active. If the timer cannot be armed, the old job is
  kept, the failure is reported and the exit status is 1: the host is never
  left with neither.

* A job whose schedule is not the one the setup wrote, or an audit script that
  has been edited, is not translated or removed: the timer is armed next to it
  and a warning says what to port by hand.

On a host under maximum security (``RevokedKeys`` in an sshd drop-in) with
no old job, it checks that ``ob-krl-refresh.timer`` is enabled and active, and
enables it if not.

What it does not do
-------------------

**It does not enrol, or re-enrol.**
   Re-enrolling mints a **new** device id, which no backend allowlist
   contains, so every hop from this host would then be refused. It is the most
   damaging thing an operator can do while trying to repair one.

**It does not touch your configuration.**
   Not ``openbastion.conf``, not the server token, not ``sshd_config``, not
   any PAM stack. Those carry decisions — a server group, a mode, an
   ``--enable-*`` flag — and a command that cannot know them must not guess.
   To change a decision, run the setup script. The one key it may add to
   ``nss_openbastion.conf`` is described above.

Options
-------

.. option:: -n, --dry-run

   Report what would change and change nothing. Does not require root.

.. option:: -h, --help

   Usage.

.. option:: -V, --version

   Version.

Exit status
-----------

``0``
   the host is up to date, whether or not anything had to be done

``1``
   something could not be repaired, or this host has never been set up

Verifying
---------

Log in with a public key from elsewhere — a password login writes no drop —
then, as root:

::

   find /run/open-bastion/ssh-fp -name '*.fp' -newermt '-2 min'

It has to be a *fresh* drop: old ones are never cleaned up, so a listing that
is merely non-empty proves nothing.
