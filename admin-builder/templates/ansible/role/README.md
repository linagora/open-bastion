# open-bastion Ansible role

This role is generated by `ob-builder` and configures one Open Bastion role:
bastion, backend, or standalone. A tree holds one such role per target role of
the build, and each of them only touches the hosts that declare that role.

## Directory layout

```
<out>/
├── site.yml                       # several roles: imports each playbook, in order
├── playbook-<role>.yml            # hosts: all, skips the hosts of other roles
├── inventory.yml.example
├── PORTAL-CHECKLIST-<role>.md
└── roles/open-bastion-<role>/     # one per target role of the build
    ├── defaults/main.yml          # Build-time defaults (baked in by ob-builder)
    ├── handlers/main.yml          # Restart sshd on config change
    ├── vars/main.yml              # Internal: setup wrapper, sshd service-keys check
    ├── tasks/
    │   ├── main.yml               # Role guard, prerequisites, APT, CA key, config
    │   └── <role>.yml             # ob-enroll + ob-*-setup
    └── templates/
        └── openbastion.conf.j2    # PAM module configuration
```

The `files/` directory (not shipped here) must contain:

- `open-bastion.gpg` — APT signing key
- `open-bastion-ca.pub` — SSH CA public key (downloaded from LLNG portal)
- `open-bastion-krl` — Key Revocation List (Mode E only)
- `sso-jwks.json` — the portal's JWKS for `ob_sso_jwks_client_id`, fetched
  from `jwks_uri?client_id=<client_id>` (trust anchor of signed answers)

## Variables

All variables are prefixed with `ob_`. Build-time defaults live in
`defaults/main.yml`; override them via host_vars, group_vars, or extra-vars.

| Variable                   | Description                                                                                                                                                                                                                                                            |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ob_portal_url`            | LLNG portal URL (required)                                                                                                                                                                                                                                             |
| `ob_client_id`             | OIDC client_id for enrollment                                                                                                                                                                                                                                          |
| `ob_verify_ssl`            | Verify the portal TLS cert; `false` (from ob-builder `--insecure`) passes `-k` and writes `verify_ssl = false`                                                                                                                                                         |
| `ob_client_secret`         | OIDC client secret — use ansible-vault                                                                                                                                                                                                                                 |
| `ob_server_group`          | Server group name (set per-host for fleet deployments)                                                                                                                                                                                                                 |
| `ob_role`                  | `bastion`, `backend`, or `standalone` — declared by the inventory (host_vars/group_vars). A host whose `ob_role` is missing or differs from the tree's is **skipped**, so one tree can be played over a mixed inventory                                                |
| `ob_artefact_role`         | The role this tree configures (baked in); do not change it                                                                                                                                                                                                             |
| `ob_pam_mode`              | PAM mode A–E (see doc/security-scenarios/index.rst)                                                                                                                                                                                                                    |
| `ob_max_security`          | `true` for Mode E (KRL, cert-only SSH, sudo via LLNG token)                                                                                                                                                                                                            |
| `ob_auto_enroll`           | Run ob-enroll during the play                                                                                                                                                                                                                                          |
| `ob_auto_setup`            | Run ob-bastion-setup / ob-backend-setup during the play                                                                                                                                                                                                                |
| `ob_apt_sources_list_line` | APT sources.list entry for the Open Bastion repository                                                                                                                                                                                                                 |
| `ob_ansible_auto_approve`  | Enable LLNG-cookie-based device-code auto-approval (build-time)                                                                                                                                                                                                        |
| `ob_llng_cookie`           | LLNG session cookie used to auto-approve — asked at every play run via vars_prompt, never stored                                                                                                                                                                       |
| `ob_become_token_cmd`      | Maximum security only: a controller-side command printing an SSO token (`llng --llng-server sso.example.com pam_token`). On a host whose `sudo` is locked to SSO tokens, it runs at every task and `sudo` gets its output; empty (default) skips such hosts. See below |

Backend-only "accept only this bastion" variables:

| Variable                      | Description                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ob_bastion_allowed_bastions` | Comma/space-separated bastion_id (as printed by `ob-bastion-id` on the bastion) the backend accepts certs from. `""` = accept any vouched bastion. Undefined = the play collects the ids from the bastions itself (ob-builder's `allowed_bastions: null`). Enforced by ob-backend-setup via the cert key-id (`bastion=<id>`) + source-address.                                                                                                     |
| `ob_bastion_group`            | Inventory group holding the bastion hosts, used for that collection (default `bastions`). Every host of the group must answer `ob-bastion-id`, or the play stops: a short list would deny hops, an empty one would accept any bastion. A bastion configured in the same run (`site.yml`) hands its id over as a host fact; any other is asked, without `become`, for the id it keeps in `/var/lib/open-bastion/bastion-id`, and only then as root. |

Signed portal answers (#339; see `openbastion.conf(5)` and UPGRADE-NOTES.md):

| Variable                   | Description                                                                                                                                            |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ob_response_signing`      | `off`, `prefer` (default: unsigned answers still accepted) or `required` (only once the portal signs; a wrong JWKS then locks out)                     |
| `ob_sso_jwks_src`          | JWKS file deployed by the role (`sso-jwks.json` in `files/`); empty = none, which requires `ob_response_signing: off` unless `ob_sso_jwks_fetch` is on |
| `ob_sso_jwks_sha256`       | SHA-256 of that file, checked by the setup run (`jq -S -c . FILE \| sha256sum`); empty = not checked                                                   |
| `ob_sso_jwks_client_id`    | The client_id the JWKS belongs to; without `ob_sso_jwks_fetch`, the play refuses a signing mode when it differs from `ob_client_id`                    |
| `ob_sso_jwks_file`         | Where it is deployed, root:root 0644 (default `/var/lib/open-bastion/jwks/sso-jwks.json`); ob-heartbeat rotates it only under `/var/lib/open-bastion`  |
| `ob_sso_jwks_force`        | `true` deploys the role's JWKS (`ob_sso_jwks_src`, or the fetched one) even over a JWKS the host already has (default `false`)                         |
| `ob_sso_jwks_fetch`        | `true`: the controller fetches the JWKS of the host's `ob_client_id` when one is to be deployed, instead of using `ob_sso_jwks_src` (default `false`)  |
| `ob_sso_jwks_url`          | Where it is fetched from, `?client_id=` appended (default `<ob_portal_url>/oauth2/jwks`)                                                               |
| `ob_sso_jwks_fetch_sha256` | Expected SHA-256 of the fetched JWKS in canonical form (`jq -S -c . \| sha256sum`); empty = not pinned                                                 |

`ob_sso_jwks_src` is deployed once. A host whose `ob_sso_jwks_file` the modules
load, and which still enrols as `ob_client_id`, keeps its JWKS on later runs:
it may hold keys ob-heartbeat rotated since the role was built. To give it the
role's JWKS anyway (a host that missed a rotation), set `ob_sso_jwks_force: true`
after rebuilding the role, so that it carries the portal's current keys.

With `ob_sso_jwks_fetch: true`, the JWKS deployed is fetched by the controller
at play time for the host's own `ob_client_id`, rather than the one `ob-builder`
fetched at build time: no rebuild after a key rotation, and an `ob_client_id`
overridden per group gets its own relying party's keys. The trust is the same
as the build's fetch, TLS from the admin side; pin it with
`ob_sso_jwks_fetch_sha256`; an `http://` URL is refused unless `ob_verify_ssl` is
false, and a JWKS holding a private member (`d`) is refused. The modules' loader (`ob-verify-response check-jwks
--anchor`) checks the file before it replaces the host's, whatever its source.

Mode-specific variables (populated by ob-builder from the selected PAM mode):

| Variable                           | Example (Mode E) |
| ---------------------------------- | ---------------- |
| `ob_cache_ttl`                     | `60`             |
| `ob_ssh_key_policy_enabled`        | `true`           |
| `ob_ssh_key_allowed_types`         | `ed25519,rsa`    |
| `ob_cache_rate_limit_enabled`      | `true`           |
| `ob_cache_rate_limit_max_attempts` | `3`              |

## Maximum security: later runs

Under maximum security (Mode E) the setup run locks `sudo` to SSO tokens on
every role: from then on the account Ansible connects with cannot become root
with a password of its own. The role does what needs root before that point
or in the setup's own task, so the run that deploys a host completes. A later
run reads `/etc/pam.d/sudo` without `become`, finds the lock, and:

- with `ob_become_token_cmd` set, plays the host: the command runs on the
  controller at every task and `sudo` gets the token it prints, so each
  elevation goes through the SSO under the name of the person running the
  play, as the scenario intends. Ansible must still be able to connect there,
  as an SSO user or a service account;
- otherwise skips it with a warning: reconfigure it by hand from an SSO
  session allowed to `sudo`, or reinstall it.

`ob_become_token_cmd` is typically `llng --llng-server sso.example.com
pam_token` (the `llng` client of simple-oidc-client). Run it once by hand
before the play, so that its session is in the cookie jar and the play never
waits for a login; set it in the `group_vars` of the locked hosts or with
`--extra-vars`. The tokens are single-use and live ten minutes; one is minted
per task, and `sudo`'s timestamp cache means most are never asked for. Only a
host found locked uses it: the run that deploys a host still takes the deploy
account's own password (`-K`, or none with `NOPASSWD`).

Backends configured by a later run still read the id of a locked bastion,
without `become`, from `/var/lib/open-bastion/bastion-id` (written by
`ob-heartbeat`), provided Ansible can still connect there. Set
`ob_bastion_allowed_bastions` in the inventory when it cannot.

## Protecting the client secret with ansible-vault

```bash
# Encrypt an inline value
ansible-vault encrypt_string 'mysecret' --name ob_client_secret \
  >> host_vars/bastion-01.example.com.yml

# Or store in a vault file
echo 'ob_client_secret: mysecret' | ansible-vault encrypt \
  > group_vars/all/vault.yml
```

Then run with `--ask-vault-pass` or `--vault-password-file`.

## Enrollment

When `ob_auto_enroll: true`, the `ob-enroll` command uses the OIDC Device
Authorization Grant flow. Two modes are supported:

### Manual approval (default)

Ansible executes `ob-enroll`, which prints a URL and an 8-character user code.
An administrator opens the URL in a browser, logs into LLNG, and approves the
code. `ob-enroll` polls the token endpoint and returns once approved.

### Auto-approval via LLNG cookie (opt-in)

If `ob_ansible_auto_approve: true` was chosen at build time, the role can
approve the device code automatically without any human interaction by
posting to LLNG's `/device` endpoint with a session cookie.

Obtain the cookie with the `llng` CLI from
[simple-oidc-client](https://github.com/linagora/simple-oidc-client):

```bash
llng --llng-server https://sso.example.com llng_cookie
```

Pass the returned cookie to ansible-playbook. The role declares a
`vars_prompt` for `ob_llng_cookie` so you can paste it interactively each
run — the value is **never persisted to disk**:

```bash
ansible-playbook -i inventory.yml playbook-<role>.yml
# > LLNG session cookie used to auto-approve device codes.
# >   Obtain with: llng --llng-server <portal> llng_cookie
# >   Leave empty to skip auto-approval and fall back to manual browser approval.
# > <paste the cookie here>
```

For CI/non-interactive use, supply the cookie via `--extra-vars` (it lives in
process memory only):

```bash
ansible-playbook -i inventory.yml site.yml \
  --extra-vars "ob_llng_cookie=$(llng --llng-server https://sso.example.com llng_cookie)"
```

The cookie's lifetime is the LLNG session lifetime (typically under 24 h),
so it's not worth persisting. An empty `ob_llng_cookie` falls back to the
manual flow above.

Under the hood, the auto-approve path:

1. Runs `ob-enroll` asynchronously on the target, with
   `OB_ENROLL_STATE_FILE=/run/open-bastion/enroll-state.json` so the user code
   and verification URI are written to disk as soon as LLNG issues them.
2. Slurps that file back to the Ansible controller, where the play `delegate_to:
localhost` performs:
   - `GET ${portal}/device?user_code=...` with the cookie, to extract the CSRF
     token from the form.
   - `POST ${portal}/device` with `user_code`, `action=approve`, and the CSRF
     token.
3. Waits for the original `ob-enroll` to finish polling and emit the server
   token to `/var/lib/open-bastion/token`.

## Example playbook invocation

```bash
# Every role of the deployment, in order (site.yml exists when the build
# produced several roles)
ansible-playbook -i inventory.yml site.yml

# First-time deployment with vault secret
ansible-playbook -i inventory.yml site.yml \
  --vault-password-file ~/.vault_pass

# Pass secret on the command line (less safe — appears in shell history)
ansible-playbook -i inventory.yml site.yml \
  --extra-vars "ob_client_secret=mysecret"

# Dry run
ansible-playbook -i inventory.yml site.yml --check --diff
```
